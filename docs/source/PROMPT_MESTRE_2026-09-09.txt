Versão inicial: 2026-09-09

======================================================================
1. OBJETIVO DO PROJETO
======================================================================

Quero desenvolver um sistema empresarial completo de check-in, inspeção e manutenção
de veículos/caminhões para uso em tablets Android dentro da oficina.

O sistema deve nascer como um produto profissional, modular, seguro, auditável,
offline-first e preparado para crescer para controle de manutenção, pneus, peças,
custos, ordens de serviço e análises futuras com IA.

O sistema será utilizado inicialmente em tablets Android com caneta, durante o
check-in físico dos veículos.

Fluxo principal esperado:

1. Funcionário faz login.
2. Identifica o veículo por QR Code, placa ou número interno.
3. Informa/valida quilometragem.
4. Abre o checklist correto para aquele tipo de veículo.
5. Inspeciona item por item.
6. Para cada item, registra:
   - OK
   - Atenção
   - Reparar
   - Crítico
   - Não aplicável
7. Pode registrar valores/medições.
8. Pode escrever observações.
9. Pode tirar fotos.
10. Pode desenhar/anotar sobre uma cópia da foto com S Pen.
11. O original da foto nunca deve ser alterado.
12. Tudo é salvo localmente imediatamente.
13. O app deve funcionar mesmo sem Wi-Fi.
14. Quando a conexão voltar, deve sincronizar automaticamente com o servidor.
15. O funcionário finaliza a inspeção.
16. O sistema registra data, hora, usuário, veículo, local e dispositivo.
17. O histórico do veículo deve permanecer disponível permanentemente.
18. Itens problemáticos poderão gerar ordens de serviço.
19. O escritório terá um painel web para visualizar a frota inteira.

2. PRINCÍPIOS NÃO NEGOCIÁVEIS
======================================================================

Este é um sistema empresarial crítico.

NÃO desenvolver como uma simples página web dependente de conexão.

O aplicativo Android deve ser OFFLINE-FIRST.

Nunca perder uma inspeção por:
- queda de Wi-Fi;
- fechamento do aplicativo;
- reinicialização do tablet;
- queda de energia;
- bateria;
- timeout;
- falha temporária do servidor.

Nunca sobrescrever dados silenciosamente.

Nunca apagar histórico de inspeção de produção.

Inspeções finalizadas devem ser imutáveis ou versionadas.
Correções devem gerar revisão/auditoria, não alteração invisível.

Toda operação crítica deve registrar auditoria.

Nunca armazenar senhas em texto puro.

Nunca colocar secrets, senhas, tokens ou chaves privadas no Git.

Nenhum agente de IA pode alterar diretamente o banco de produção.

Toda alteração de schema deve usar migrations versionadas.

Toda funcionalidade relevante deve vir acompanhada de testes.

Nenhuma decisão arquitetônica importante deve ser trocada sem documentação ADR
(Architecture Decision Record).

6. REQUISITO CRÍTICO: SINCRONIZAÇÃO OFFLINE
======================================================================

A sincronização é uma das partes mais críticas deste produto.

Projetar desde o início:

- IDs UUID gerados no cliente para objetos criados offline.
- Fila local de operações pendentes.
- Idempotência no servidor.
- Retry com backoff.
- Estado de sincronização visível.
- Upload resiliente de fotos.
- Checksum de arquivos quando necessário.
- Não duplicar inspeção por retry.
- Não duplicar foto por retry.
- Registrar data/hora local e data/hora recebida no servidor.
- Resolver concorrência de forma explícita.
- Nunca usar "last write wins" cegamente para dados críticos.
- Definir claramente quais registros são append-only.
- Definir política para dois tablets operando sobre o mesmo veículo.
- Testar tablet offline por horas/dias e posterior sincronização.
- Testar app encerrado no meio da operação.
- Testar rede caindo durante upload.
- Testar rede oscilando.

Criar documento obrigatório:
docs/OFFLINE_SYNC.md

Antes de implementar sincronização, fazer revisão arquitetônica dedicada.
